# 承認済みフィルタージョブ（Issue #5）

最終確認で承認すると、Web要求は `ACCEPTED` と RunId を返します。Gmail変更はこの要求の中で実行せず、所有者の時間主導トリガーが実行します。Webを閉じても続き、起動時と「保存済みのフィルター適用状況を確認」で進捗を復元します。既存メールを処理する `Messages` ジョブとは別です。

## 確認準備と実行

確認準備も `prepareStart` → `prepareStatus` の保存済み処理です。READ、BACKUP、VERIFY_BACKUP を別のトリガー呼出しで進め、READY で初めて最終確認画面を返します。各段階の時間は準備状態に保存します。この間にGmailは変更しません。新しい準備を開始すると古い承認準備は失効します。

承認後は SHEET_READ、DIFF_CHECK、BACKUP_CHECK、REFERENCES、APPLY、FINAL_REFERENCES、VERIFY を保存しながら進めます。初期準備は1段階ずつ、参照更新は最大25行ずつ、適用は1呼出し最大10段階、経過90秒を目安に区切ります。個別のGASサービス呼出しの途中を強制的に中断することはできません。サービス自体が長時間停止した場合は、次回の状態確認とリース期限で検知します。

トリガーは `GFM_runFilterJob` 用を1個だけ作成し、1分間隔で動かします。他用途のトリガーを削除しません。正常完了・要確認停止では専用トリガーを削除します。所有者の ScriptLock が受け付け・実行・修復を直列化し、UserLock がログ枠の予約を直列化します。バックグラウンドも保存済みスプレッドシートIDを開き、実行者と実際の所有者を再確認します。MYSELF / USER_ACCESSING の非公開Web設定は維持します。

ジョブは最大24時間、最大1000回の実行、連続障害5回を上限とします。150秒のリースが切れた RUNNING や専用トリガーの消失は状態確認時に修復します。トリガーが存在しても5分間更新がなければ再登録し、修復を3回繰り返しても更新しない場合は PAUSED にします。割り当て・認可・サービス障害の確認が必要です。

## 状態と確認済み件数

- ACCEPTED: 受付済み。予定件数とRunIdを保存済み。
- RUNNING: 所有者の実行権を取得して処理中。
- WAITING: 保存した位置から自動続行待ち。再承認不要。
- PAUSED: 中断・要確認。停止理由と結果不明の件数を表示。
- OK: 承認対象の反映と全体照合を確認済み。

予定・反映確認済み・残りをラベル／フィルター別に表示します。単なるNOOPやGmail側のみのフィルターを成功件数へ加算しません。既存IDの採用は確認対象に含めます。中断置換の旧ID削除が別途必要な場合は、確認画面に明示した削除操作も1件として数えます。現在工程・最終更新・ハートビート・工程別の累積時間は保存済み状態から取得します。ポーリングはGmail変更を再送しません。

## 中断・編集と復旧

Gmail作成前に CREATE、削除前に DELETE、ラベル反映前に LABEL の実行意図を永続化します。API応答を失った場合は、保存した元ID集合と内容からGmailの現状を照合します。作成候補が一意に確認できなければ結果不明として停止し、自動で作り直しません。置換は新規作成・内容照合を終えた後に旧IDを削除します。

シートの値とGmailの全体状態を保存済みの期待値と比較し、他の編集を検知した場合は未実行の変更を止めます。メタデータや参照の更新も意図を保存し、応答消失後は旧値／予定値だけを許して照合します。反映件数の確定はメタデータ更新後のCOMMITで行い、同じ作成を再送しません。

PAUSED の「残りの差分を確認して続ける」は、元の選択キーと依存ラベルの範囲を引き継いだ新しい確認準備へ進みます。まず結果不明を照合し、確定したID等のシステム列だけを復旧します。Gmailを変更せず、編集後の内容と必要な旧ID削除を新しい確認画面へ表示します。新しい依存ラベルが元の範囲外なら停止し、選択を明示的に見直す必要があります。曖昧な作成候補や変更済みの旧IDは自動で解決しません。バックアップを消してやり直さないでください。

## 保存とサービス呼出し

Script Properties に置くのは所有者・ブック・RunId・期限・件数・小さなポインター等です。承認済み行、元JSON、選択キー、期待状態、更新意図とチェックポイントは Backup のハッシュ付き分割データへ追記します。既存 `MESSAGES` 分割保存形式を共用しますが、メール処理ジョブを実行するものではありません。元のバックアップは残します。履歴が増えるため、シート容量の監視は引き続き必要です。

参照・メタデータは行メタデータIDを使って最大25行を1つの Values API要求で更新し、前後のスナップショットで定義とシステム列を照合します。行番号のキャッシュで更新しません。更新するシートごとにDeveloperMetadata.searchのJSONを1回読み、重複を拒否した値→IDのMapを作ります。25行・1,200アンカーの一括パッチではgetValue/getId/Finder各0回、メタデータ検索5回（更新用1回＋前後のFilters/Labels読取各2回）、Values API書込1回です。旧経路のgetValue 30,000回・getId 25回というサービスオブジェクト呼出しを除去しました。単一行のシステム列・ラベル参照更新も同じJSONマップを使用します。バックアップ・選択票・大きな元JSONは対象IDをサーバー側で検索し、隣接行をまとめて取得します。過去のジョブや既存メールの本文データ全体を読み直しません。

## 任意Cloudログの制御

`exceptionLogging: NONE` を維持し、自前Cloud出力も既定OFFです。通常は保存済みジョブとHistoryを使います。運用GASのCloud環境を確認し、任意ログを有効にする場合だけ Script Property `GFM:cloudLoggingEnabled` をJSONの `true` にします。停止は `false` またはプロパティ削除です。

通常出力は異常・復旧・10秒以上の重要な遅延の短い要約です。診断時だけ `GFM:logDiagnosticsUntil` を終了時刻のUnixミリ秒に設定すると工程ログを追加できます。既定は未設定、終了時刻を過ぎると自動的に出なくなります。診断時も同じ枠を使います。

出力はRunIdまたはそのハッシュ、許可済み工程／エラーコード、数値の件数・時間だけです。任意文字列や生の例外を渡しません。メールアドレス、検索条件、ラベル名、原本JSON、認証情報はCloud出力へ載せません。出力前に2KiB以下、1ジョブ20件、UTC日次100件の枠を別ロックで永続予約し、同じイベント・工程・エラーコードを集約します。日次枠は複数のトリガー実行をまたぎます。ロガー・出力先・枠保存が失敗しても適用と利用者向け状態は続きます。保存失敗は出力を抑制する側に倒します。Googleが自動生成するログや他のサービスのログには、この枠は適用されません。

2026-10-27の親タスクの読み取り監査では、運用GASはデフォルトCloudプロジェクトで、管理用のバケット・保存先・使用量を直接確認できませんでした。インストーラーが使う標準プロジェクトとは別です。その標準プロジェクトでは _Required と _Default の同一プロジェクト宛シンクだけで、任意の転送／重複シンクはなく、_Default は30日でした。_Required の400日は必須監査ログのロック済み保持であり変更しません。これを運用GASの設定・使用量と同一視しません。

任意Cloud出力は、実際の運用プロジェクトで保存30日以内、不要な転送・重複保存なしを確認できるまでOFFにします。今回、Cloudプロジェクトの付け替え、APIや有料サービスの有効化、保持延長、BigQuery転送、新しい課金監視は行っていません。課金・使用量の参照はAPI有効化に関する制限で未確認です。無料枠内や費用上限を保証するものではありません。

## 再現できる性能比較

`node scripts/benchmark-jobs.js` は本物のSheetsアダプターを合成サービスで動かします。108フィルター、ラベル30作成・20改名の同じ対象で、旧同期処理と新ジョブを比較します。実Gmail・認証・ネットワークは使いません。両者が触るGmail変更は50操作で同じです。

| Sheets DeveloperMetadata.search（JSON取得） | 1966 | 426 |
| DeveloperMetadata getValue / getId / Finder | 0 / 0 / 0 | 0 / 0 / 0 |

計測対象メソッド呼出しは53.5%減、メタデータ更新は77.4%減です。新処理はさらに313回の論理チェックポイントを保存します。その実際のシート読取・書込・flushは上記の呼出しに含まれます。計測区間はapply／acceptから完了までで、初期設定・承認準備を含みません。TextFinder、getRange、シート属性取得、RichTextValue構築、Properties、ロック、トリガーAPIは合計に含めません。サービス内部のキャッシュ・一括処理によりメソッド呼出しとネットワーク往復の数は一致しないため、網羅的なRPC計測ではありません。

1呼出しを25msと仮定した決定的なシミュレーションでは、合計339950ms→158100ms、旧処理の単一呼出し339950msに対し、29回のジョブ実行で最長10675msでした。Nodeの処理時間は約1.6秒→0.7秒でしたが、端末によって変動します。これらは実GASサービスの実測時間やトリガー待ち時間ではありません。本番サービスの停止位置・時間は保存済みtimingsから追加確認します。

## レビュー補強（Issue #5）

保存済みチェックポイントの読込と期待状態の再構築も障害処理の対象です。ハッシュ・JSON・形式の破損は直ちに要確認停止し、一時的なサービス障害は最大5回で停止します。元の保存位置と結果不明の情報を維持して、停止理由をHistoryへ残します。続行前のシステムID復旧は、現在の関連付けが承認時の元IDまたは一意に照合した新IDの場合だけ行い、手動のID変更は上書きしません。画面再表示では、実行中ジョブ、より新しい確認準備、過去の終了済みジョブの順で復元します。

## 参照更新の診断と先頭シート

Advanced Sheetsの応答では `sheetId: 0` が省略される場合があります。Filtersの行メタデータは省略値を0として扱います。旧版で繰り返し作成された、同じ対象キー・同じ物理行のメタデータは最小IDの1件として読み取ります。異なる行への重複・行とキーの不一致は引き続き拒否します。既存のメタデータを削除して復旧する必要はありません。

参照・メタデータの一括更新に失敗した場合、保存済みジョブとHistoryのVerificationには `diagnostic` を記録します。保存するのは許可した `code`、`stage`（PRECHECK / WRITE / READBACK）、対象件数（最大25）、許可したサービスステータス、発生時刻、試行回数、固定の操作名のみです。サービスの例外全文、フィルター定義、メールアドレス、任意の例外プロパティは保存しません。408 / 429 / 5xxなど分類できた一時障害だけを最大5回再試行し、入力・行関連付け・定義変更・読み返し不一致・拒否・分類不能の例外は停止します。停止したジョブを自動再開せず、残りの差分を再確認します。
