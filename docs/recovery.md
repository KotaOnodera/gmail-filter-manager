# 障害時の確認・復旧

このツールは自動ロールバックを行いません。Gmailのフィルター更新はトランザクションではなく、復旧後のIDも元と同じになる保証はありません。メールの転送や既存メールへの影響を取り消すことはできません。

## まず確認すること

1. Applyの連打を止める。Gmail画面とFiltersの同時編集も止める。
2. Historyの最後のRunId、SnapshotId、エラー、変更前後IDを確認する。
3. Backupの該当SnapshotIdにCOMPLETEがあることを確認する。FILTERとCONTEXTの全分割パートが揃い、ハッシュが一致することが必要。
4. 必要ならファイルを手動で保全する。Backupの行や隠し原本列、DocumentPropertiesの中断状態は消さない。
5. 「差分をプレビュー」を実行する。中断ジャーナルがある場合はGmailを読み直し、可能ならID記録だけを復旧する。この段階でGmailを書き換えない。
6. 復旧可能な差分を確認し、新たなバックアップとYes/No承認を経て適用する。

## 状況別の動作

| 状況 | 残る状態と対応 |
| --- | --- |
| バックアップ失敗 | Gmail変更0件。容量・権限・破損を解消して再Dry Run |
| 承認でNo | GmailとFiltersの定義は不変。作成済みバックアップとキャンセル履歴は残る |
| 50変更/4分の予算で停止 | PARTIAL。適用済みIDは保存。次のDry Runと承認で未適用分を続行 |
| 新規作成成功、新ID保存に失敗 | 次のDry Runが新フィルターを照合してIDを復旧。作成を繰り返さない |
| 新規作成成功、旧フィルター削除に失敗 | 次のDry Runに「中断したREPLACEの旧フィルター削除」が出る。内容が一致する場合だけ、新しい承認で旧IDを削除 |
| 削除は成功したが応答/行更新に失敗 | 次のDry Runが旧ID不在を照合し、システム列を修復。削除の重複実行を避ける |
| 作成応答が失われた | バックアップに存在しなかった同等フィルターが一意の場合だけID復旧。候補0件/複数なら止まる |
| Filters行を誤削除 | Gmailは残存しREMOTE_ONLYになる。「既存フィルターを取り込む」で確認して追加。元RuleKeyが必要なら保全した行を戻す |
| プレビュー後にシート/Gmailを変更 | 適用前に停止。再Dry Runで変更内容を確認 |
| 未知フィールド/ラベル不明 | 原本は維持。定義を理解して修正するか、Gmail側で扱う。黙って原本JSONを削らない |

中断した置換の新フィルターやFiltersが変更されていたら、自動で旧フィルターを削除しません。まず期待した新定義に戻すか、以下の手動監査で新旧を確認してください。

## 作成結果が確定できない場合の手動監査

候補0件は「書き込みが絶対に起きなかった」という証明になりません。APIの反映遅延や通信断を考慮し、Gmail画面/APIとHistory/Backupを照合します。

1. スプレッドシート所有者が、対象RuleKey、意図したcriteria/action、旧ID、現在の同等フィルターを確認する。
2. 同等フィルターがあればどれを管理するかを明示し、FiltersのGmailFilterIdをそのIDへ修正する。重複があれば、削除対象・影響を別途承認した上でGmail画面等で処理する。
3. 存在しないことを確認して再作成すると決めた場合は、FiltersのGmailFilterIdを空欄にする。
4. 調査記録をHistoryに手動追記し、所有者が**中断状態のリセットを明示的に決定した場合だけ**、Apps Scriptエディタで次の一時関数を実行する。

```js
function resetGfmAfterOwnerAudit() {
  // 所有者がGmailの現況を照合し、IDと残存重複を整理した後だけ実行する。
  const p = PropertiesService.getDocumentProperties();
  ['pending', 'cleanup', 'preview', 'prepared'].forEach(
    key => p.deleteProperty('GFM:' + key)
  );
}
```

これはDocumentPropertiesです。ScriptPropertiesを消しても復旧しません。一時関数は確認後に削除し、Dry Runで差分を見直し、改めて承認します。状態リセット自体はGmailを書き換えませんが、誤って行うと次回の二重作成防止を解除するため、機械的に実行しないでください。

## バックアップから元定義に戻す独立した操作

**所有者が復元対象・変更内容を指定し、明示承認したときだけ**行います。過去スナップショットを無断で全面再適用しません。

1. 現在のシートとGmailを保全し、復元に使うSnapshotId・対象フィルター・希望状態を決める。
2. 対象SnapshotIdのFILTERのJsonをPart順に結合する。Hash、Parts、全件数、MANIFESTとCOMPLETEを確認する。CONTEXTから当時のラベル名とIDを確認する。
3. 原本criteria/actionから対象のFilters行の編集列を復元する。OriginalJsonとOriginalRowJsonの対応も維持する。大きな原本はBLOBの参照を保持する。現在のIDを使用し、古いIDを有効なIDだと仮定しない。
4. ラベルIDが変わっていたら、現在のUserLabel名とAdditional配列を修正する。未知フィールドを再作成できない場合は停止し、APIの現行仕様を確認する。
5. 復元後に不要となる現行フィルターは、別途その行を「削除予定」にする。行削除では消えない。
6. Dry RunでCREATE/REPLACE/DELETEの全対象を確認する。復元でも新しい直前バックアップと承認が必要。
7. 適用後に「同期結果を検証」、History、Gmail画面を照合する。

元のフィルターIDの維持、既に発生した転送の取消し、メールのラベル状態の巻戻しは対象外です。原本に将来追加フィールドがある場合、現行コードが受け付けるよう明示的に更新するまでその再作成はブロックします。

## インストーラーの作成中断

インストーラーの状態は、運用GASのDocumentPropertiesとは別の、スタンドアロンGASのScriptPropertiesにあるGFM_INSTALL_STATEです。通常は削除せず、同じインストーラーでGFM_installを再実行します。

- シート準備の失敗: 記録した同じスプレッドシートで再開します。
- フォルダへの配置失敗: 作成済みスプレッドシートIDを保持して停止します。未配置のファイルがマイドライブ直下に残る場合があります。元の指定フォルダの権限・API設定を直して再実行すると、同じファイルを配置します。既に移動が成功していれば再移動しません。作成途中では保存先プロパティを変更しないでください。
- ソース配置の失敗・応答不明: 記録した同じGASを読み返します。同梱ソースと一致していれば完了とし、配置前の内容のままなら同じPUTを再実行します。手動変更は上書きしません。
- スプレッドシート/GASの作成応答不明: 自動再作成を止めます。DriveやApps Scriptの一覧から作成済みかを所有者が確認してください。

作成済みIDを確認できた場合だけ、インストーラーのエディタで一時関数を追加して復旧します。

```js
function recoverInstallerAfterOwnerAudit() {
  // スプレッドシート作成の応答不明だった場合:
  GFMInstaller.runtime().recover({spreadsheetId: '確認したID'});
  // GAS作成の応答不明だった場合は、上の行の代わりに:
  // GFMInstaller.runtime().recover({scriptId: '確認したID'});
}
```

所有者・GASの親ファイルを検証し、手動ソースがあるGASへの復旧は停止します。復旧後にGFM_installを実行してください。Google APIの反映遅延も考慮して、何も作成されなかったことを所有者が確認した場合に限り、recover({notCreated: true})で作成intentを解除できます。これは重複防止を解除する明示的な判断です。

初期状態を確認する前に手動コードが追加された場合、空のプロジェクトであると仮定せず停止します。コードの更新時にもGASエディタや別のclaspから同時に編集しないでください。Apps Script APIの読み取りとPUTはトランザクションではなく、その間の別編集を完全に排除する仕組みはありません。


## 既存メール処理の中断・失敗

Webの「保存済みの既存メール処理を確認」で対象延べ件数・処理済み・未処理・結果不明とエラーを確認します。起動時にメールを検索し直したり、自動で変更を再送したりしません。検索の保存地点は「ここまで検索済み・続行待ち」と表示し、「対象メールの検索を続ける」で次バッチを取得します。検索に失敗した場合は原因と「検索を再試行」を表示し、保存した検索カーソル・対象IDを維持して続けます。検索完了までは検索済み延べ件数であり、総対象件数は未確定です。検索済みなら内容を再確認して「確認した既存メールを処理する」で続行します。

検索の応答喪失と検索失敗は別です。応答がないだけでは失敗・完了・実行継続を断定せず、「状況を更新」で同じリクエストを確認します。古い実行記録が未確定のままの場合は、操作画面から「保存済みの既存メール処理を確認」を開きます。実行中の要求と排他して取得できた保存済み状態から手動で続行します。保存済み状況の取得は30秒でタイムアウトし、同じ実行IDで再確認できます。検索・メール変更の自動再送や自動承認は行いません。再読み込み時も保存済みの同じ実行IDと対象を使い、状態が進んだ古い適用確認は再利用しません。

同じRunIdのHistoryにはMESSAGESコマンドでSCANNING/SCAN_FAILED/READY/RUNNING/PARTIAL/FAILED/OK/CANCELLEDと件数を記録します。API更新前に対象バッチの意図を保存します。応答不明・GAS強制終了の場合は未処理として残るバッチを再適用できます。応答を得られた件数だけを処理済みに数え、結果不明は未処理件数の内数です。API例外はバッチ全体を失敗・結果確認待ちとして扱います。

BackupのMESSAGESには条件・処理内容・メールIDを保存します。メール本文は記録しません。データはハッシュと分割番号を読み返して検証します。保存範囲が移動・破損した場合は続行せず、スプレッドシートの変更履歴などで元の配置と内容を復旧してください。結果は実行IDのHistoryから確認できます。BackupとScript Propertiesは復旧が終わるまで削除しないでください。

対象の定義やラベルが変わった場合は、確認画面の「内容を再確認」から残りを中止し、保持できる選択を最新一覧へ戻して対象を明示的に検索し直します。期限切れだけなら保存済みの同じIDと最新件数で再確認します。中止しても処理済みのメールは元に戻りません。既存メールへの変更前の状態を自動復元する機能はありません。

## ラベル作成・改名の中断

GFM:labelPendingはラベルAPIの直前に保存されます。再プレビュー時にGmailを読み返し、作成時はバックアップに含まれない同名ラベルを一意に照合し、改名時は同じIDの名前を確認してからLabelsのIDと参照名を復旧します。作成候補が0件/複数件、定義が編集済み、名前がさらに変わっている場合は自動再作成しません。対象実行IDのログとBackupのCONTEXTを確認してください。

ラベルの作成・改名は完了している一方、フィルターの反映は未完了の場合があります。復旧後の新しい差分と承認で残りを反映します。Gmailはラベル作成/名前変更/フィルター変更をひとつのトランザクションでは実行しません。手動でlabelPendingを消して再実行すると重複の原因になります。

## 承認済みバックグラウンドジョブ（Issue #5）

新しいWeb適用は受付後に自動継続します。ACCEPTED / RUNNING / WAITING は「保存済みのフィルター適用状況を確認」へ進み、同じ変更を再送しないでください。PAUSED は結果不明の照合後に「残りの差分を確認して続ける」で、元の選択範囲を保った確認へ進みます。詳細な中断点、期限、トリガー修復、ログ制限は[バックグラウンドジョブ](background-jobs.md)を参照してください。バックアップは削除しません。


## 承認前の画面を閉じた場合

同じタブを再読み込みすると、保存した差分・選択・確認段階を復元します。元の通信が完了して応答だけ失われた場合も、保存済み表示を読み出します。確認が期限時刻に達した場合や、設定・Gmailの変更／別操作で失効した場合は、表示した期限と理由を確認し「内容を再確認」へ進みます。元の選択を可能な範囲で保持し、消失・変更・適用不可の対象と依存ラベルを再確認します。承認チェックは外れ、新しい内容を明示的に承認するまで変更を実行しません。保存結果が不明・破損・24時間経過の場合は「取得し直す」を使ってください。保存済み画面の取得は30秒を上限とし、通信タイムアウト時の「取得し直す」は同じ保存済みIDを読み直します。復元や通信タイムアウトの再試行による確認準備・バックアップの再作成や適用の自動再送はありません。保存前に破棄された最後の選択変更は選び直してください。詳細は[差分・確認画面の保存と復帰](mobile-web.md#差分確認画面の保存と復帰)を参照してください。


## 一覧に入力エラーがある場合と設定編集後の再確認

差分・選択適用・既存メールの対象一覧で「入力エラーのみ表示」を使い、Filters／Labels、対象キー、修正理由を確認します。該当カードの設定リンクは、管理対象ブックのシートまたは取得時に照合できた行を新しいタブで開きます。並べ替えた場合はキーで対象を確認してください。元画面の表示と選択は残ります。

修正後は差分または対象一覧を再取得し、最新の対象を選んで再確認します。最終確認を表示中なら「内容を再確認」で保持できる元選択と変更された対象を確認し、新しい承認チェックを入れます。設定リンクを開くと古い一覧からの次の確認を止め、最終承認のチェックを外します。サーバーも設定変更を再検証するため、直接シートを編集した後の古い票では適用できません。全部適用では入力エラーを黙って除外しません。正しい対象だけを扱う場合は明示的に選択適用へ切り替えます。

絞り込みを解除しても選択は変わりません。表示だけを狭めた後の確認には非表示の選択も含まれます。「表示中の選択可能な対象を解除」は非表示の選択を解除しないため、全体の選択件数・非表示の選択件数と、次の確認の対象を確認してください。


## 旧同期処理から更新した際の置換中断

旧版で新フィルター作成の応答を失った場合は、最初に差分をプレビューします。元バックアップにない作成候補が一意なら新IDを復旧し、旧フィルターの削除を新しい確認へ表示します。新旧のID、内容、Filtersの関連付けが一致しない場合は自動で削除・再作成しません。

Webの全部適用・選択適用、またはメニューの承認では、復旧対象の旧フィルターDELETEを確認します。選択適用から復旧対象を除外できません。新しいジョブは旧復旧記録のハッシュ、承認済みデータ、所有者・ブック・選択範囲との対応を保存し、承認した旧IDだけを削除します。受付だけでは旧復旧記録を消しません。新IDを維持し、旧IDの不在とシートの関連付けを確認した後に解消します。古いバックアップは残ります。

削除の応答を失った場合も同じジョブが照合を続けます。停止した場合は「残りの差分を確認して続ける」で元の選択範囲を復元します。旧IDが残っていれば削除を再確認し、既に削除済みなら新IDと関連付けを検証して復旧記録を解消します。手動のID変更・Gmailの内容変更・曖昧な作成候補は自動で採用しません。
