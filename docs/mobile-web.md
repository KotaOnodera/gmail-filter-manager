# スマホ用Web画面

Web画面は実行専用です。次の操作を利用できます。

| 操作 | 内容 |
| --- | --- |
| インポート | Gmailの既存フィルターとラベルをスプレッドシートへ追加。既存の編集を維持 |
| 全部適用 | Filters/Labelsから差分を取得し、確認後にまとめてGmailへ反映 |
| 選んで部分適用 | 差分からフィルター・ラベルを選び、依存ラベルを含めた確認後に反映 |
| 既存メールへ適用 | 有効な定義に一致するメールへラベル付与・アーカイブ・既読化 |
| 実行ログ | 日時・結果・エラー・バックアップIDを表示 |

Webには新規作成や編集フォームはありません。設定の編集は従来どおりスプレッドシートで行います。フィルター一覧やGmailデータは起動時に取得せず、操作画面を先に表示します。起動時の通信は未確認の前回結果と保存済みの既存メール処理の概要の確認だけです。実行ログの表示もGmailやFiltersの読み出しに依存しません。

## 配置

1. `npm test`、`npm run check`、`npm run build`を実行します。
2. 新規導入は通常のインストーラーを利用します。既存導入では更新したインストーラーの`GFM_updateInstalledCode`を実行します。配置先を手動変更すると整合性確認が停止します。
3. 初回のみ、**スプシに紐付く運用用GAS**で所有者が`GFM_enableWeb`を実行します。対象IDと共有状態を初期化します。メニューとWebは同じScriptProperties・ScriptLockを使用します。
4. 運用用GASを「ウェブアプリ」としてデプロイします。実行ユーザーは「アクセスしているユーザー」、アクセス範囲は「自分のみ」（`USER_ACCESSING` / `MYSELF`）です。
5. `/exec` URLをSafariで開いて所有者アカウントでログインします。「ホーム画面に追加」で起動用アイコンを置けます。

更新時は既存のWebデプロイを新しいバージョンに更新すればURLを維持できます。利用URL・作成先ID・個人設定を公開ソースに埋め込む必要はありません。既存メール処理には運用用GASの`gmail.modify`スコープが必要です。コードの更新に加えてWebデプロイを更新し、所有者アカウントで追加権限を再承認してください。インストーラーの権限は増えません。

## 適用の流れ

全部適用と選択適用は、どちらも最新の差分を取得します。変更前後と注意事項を確認し、「確認へ」からバックアップを作成・検証します。その後、確認チェックと適用ボタンで実行します。確認は15分で失効します。Gmailやスプシが変わった場合は再確認が必要です。

選択適用は最初は未選択です。選択したRuleKeyと依存ラベルキーの集合をBackupのSCOPEレコードとして分割保存・読み返しし、承認にはそのハッシュと件数を結び付けます。適用時はクライアントの新しい選択を受け入れません。選択外のフィルター定義は反映せず（共有ラベルの参照名は追従）、成功判定も選択対象に限定します。残っている差分の件数を完了画面に表示します。選択外に入力エラーがあっても、選択した対象が有効なら部分適用できます。復旧中の置換がある場合は、その復旧対象を含めて選択する必要があります。

Gmail側にしかないフィルターは自動削除しません。「無効」「削除予定」は反映時にGmail上の定義を削除する既存の仕様です。

## 既存メールへ適用

1. 必要に応じて「全部適用」「選んで部分適用」でGmailのフィルター設定を反映します。
2. 「既存メールへ適用」を開き、有効な定義の全件、またはチェックした対象を検索します。未反映のシート定義を使うこともできます。無効・削除予定の行は対象外です。実行できる3処理がない定義は選択できません。Labelsで新規作成・改名が未反映の参照先は、先にフィルター設定の反映から同期してください。既存メールの処理だけでラベルを作成・改名することはありません。
3. 大量の場合は「対象メールの検索を続ける」で検索を進めます。検索中はメールを変更しません。対象は推定値ではなく、保存したメールIDから件数を数えます。
4. 検索完了後、「既存メールへの適用を確認」でフィルター別の件数、ラベル付与・アーカイブ・既読化、実行しない処理を確認します。確認チェックと専用ボタンで実行します。
5. 部分完了・失敗の場合は、状況とログを確認し、もう一度内容を確認して続行します。自動処理や時間トリガーは追加しません。

メール単位のAPIで処理し、同じスレッド内でも条件に一致しないメールには適用しません。対象は検索開始時刻より前のメールです。迷惑メール・ゴミ箱・下書き・送信済みは除外します。検索結果は時点をまたいで取得するため、Gmailの検索インデックス反映や外部からの変更により厳密な同時点スナップショットにはなりません。検索完了後は保存済みのIDだけを使用し、後から届いたメールを追加しません。同じメールが複数定義に一致した場合はフィルターごとに処理し、件数は**延べ件数**で表示します。

From、To（Cc/Bccを含む）、件名、Query、NegatedQuery、添付あり、チャット除外、サイズ条件をGmail API検索へ変換します。OR・否定は括弧で囲み、条件同士をANDで結びます。件名は連続する空白をまとめたフレーズで検索します。安全に変換できない括弧・引用符・制御文字・バックスラッシュや未認識の条件は実行を停止します。HasAttachment/ExcludeChatsのFALSEとサイズ比較unspecifiedは検索を制約しません。Gmail UIとAPIの検索は、アドレスのエイリアス展開などに違いがあります（[Googleの説明](https://developers.google.com/workspace/gmail/api/guides/filtering)）。

各リクエストは原則20秒・最大5ページ/バッチを目安とし、検索1ページ500件、更新1バッチ100件までに区切ります。各API呼び出し自体が遅延した場合は、この目安を超えることがあります。対象定義・メールIDはBackupのMESSAGESレコードへ分割保存し、Script Propertiesには小さな進捗だけを保存します。Backupを削除・並べ替え・直接編集すると対象の検証で停止します。検索後に選択した定義やラベルが変わった場合も更新前に停止するため、処理を中止して対象を再検索してください。

「残りの処理を中止する」は未処理分の続行を止めます。既に処理したメールを元に戻す機能はありません。更新APIの応答を失ったバッチは結果不明として未処理件数に含め、明示的な続行で同じIDへ再適用します。3処理は冪等なので、ラベル重複や転送などの副作用を起こしません。手動でラベル・未読・受信トレイを変更した場合は、再適用で確認済みの状態に戻ります。

## ラベルの反映

Labels.Nameが正です。確認画面でラベル作成/名前変更の前後を表示し、Gmail側が違う場合はシートの名前へ上書きします。選択フィルターに必要な管理ラベルもサーバーで選択対象へ追加し、承認画面に表示します。名前変更は同じラベルを使うメール・選択外のフィルターにも表示名が反映されます。選択外のフィルター定義自体は反映しません。

新規ラベルを先に作成・検証してからフィルターを反映します。名前のみ変わる場合はフィルターを作り直しません。選択件数と集計にはラベルを含みます。各ラベルをフルパスで管理し、希望名重複や別IDの同名ラベルはエラーです。

## 通信断・ログ

通信が切れても適用を自動再送しません。結果不明の画面で実行IDを表示し、保存済み結果か同じ実行IDのログを確認できます。未確認の結果はサーバーに保持し、再読み込み後にも表示します。部分完了や復旧が必要な場合は[復旧手順](recovery.md)を参照してください。

スプシへの直接のセル編集はGASのロックに参加しません。Webで適用する間は同時の直接編集を避けてください。全行とGmailのfingerprintを承認時・適用時に照合しますが、Sheets APIに条件付きセル更新のトランザクションがないため、外部編集との極めて短い競合区間は完全には排除できません。

## デザイン・ローカル検証

[デジタル庁デザインシステム](https://design.digital.go.jp/dads/)のカラー、文字、ボタン、入力欄、結果表示を参考にした独自HTML/CSSです。ロゴは使っていません。UIの外部CDN依存はありません。

`node scripts/preview-web.js`で合成データのプレビューを起動し、`http://127.0.0.1:4179/`で操作できます。`GFM_PREVIEW_CHANGES=1`を付けると2件の差分、`GFM_PREVIEW_LOST_APPLY=1`を付けると適用応答の喪失を再現できます。実際のWeb/Sync/Sheetsのコードにテスト用Googleサービスを接続し、実アカウントは変更しません。このサーバーはGASへ同梱されません。

既存メールの応答喪失は`GFM_PREVIEW_LOST_MESSAGES=1`で再現できます。ローカルの既存メールは合成IDと模擬更新のみです。


## 画面を離れた場合

画面を再表示したとき（visibilitychange/pageshow）は、待機中の古い応答から画面を切り離し、保存済みのリクエストIDで状況を取得し直します。通常の応答待ちが45秒続いた場合も、状況確認画面へ切り替えます。状況確認自体には10秒の待ち時間上限があり、失敗しても再確認できます。

設定適用の結果、インポートの結果、既存メールの検索・処理状況を復元できます。結果確認では変更処理を自動再送しません。受け付けたか分からない場合や、サーバー処理の状態が7分以上更新されない場合は、未確定として表示します。変更操作の古い応答が後から返っても、復元後の画面や別の操作を上書きしません。差分・確認画面などの読み取りは、同じ処理の状況確認中なら遅れて届いた表示データを利用できます。別の操作へ進んだ場合は、その読み取り応答も破棄します。

再読み込み対策としてsessionStorageへリクエストID・操作名・実行IDと、表示済み画面の参照IDだけを保存します。承認トークンやメールの定義は保存しません。埋め込みブラウザで保存が拒否された場合も、同じページ内の復帰処理とサーバーの既存結果保存を使用できます。サーバーのリクエスト別記録は直近32操作を保持し、それより古いものは実行ログで確認します。メール処理は開始時点でリクエストIDと実行IDを同じチェックポイントに保存します。復帰用のresume APIは所有者の小さなチェックポイントだけを読み、Gmail/Filters/Backupの取得や実行ロックを必要としません。

この対応は開始済みの1回分の処理と画面復帰のためのものです。大量メールの検索・適用は従来どおり分割し、部分完了後の次の実行には確認が必要です。画面を閉じたまま全バッチを自動完了するスケジューラーは含みません。

適用カード内の長いラベル名・検索条件・アドレス・ID・JSONは画面幅内で折り返します。文字数で値を切り詰めず、スマホでは変更前後を縦に表示します。


## 差分・確認画面の保存と復帰

差分、全部／選択適用の確認、インポート確認、既存メールの対象一覧と適用確認は、表示データをサーバーへ保存します。同じタブの再読み込みでは、通信中ならリクエストの状況を確認し、表示済みなら保存済み画面を取得します。元の応答が届かなくても、完了記録から表示結果を取り出せます。取得には10秒の上限があり、失敗・期限切れ・不明の場合は「取得し直す」または「操作に戻る」へ進めます。

選択適用では操作段階、ALL/SELECTEDと選択キーをサーバーで保持します。チェックを変更するたびに保存し、失敗時は画面上で案内します。保存がサーバーへ届く前にタブを破棄した場合、その最後の変更は戻らない場合があります。確認画面から「差分に戻る」は元の保存済み差分とユーザーの選択を開きます。確認に追加した依存ラベルを、ユーザーが直接選択したキーへ追加しません。「差分を再取得」または「取得し直す」を押した場合に、新しい差分を計算します。

復元ではプレビュー・バックアップ作成・適用を自動再実行しません。確認チェックは毎回未選択で、適用には再び明示的な承認が必要です。別の差分確認、設定変更、確認の15分期限で失効した確認内容は、適用可能な確認画面として復元しません。承認済みのフィルタージョブがあれば保存済みの進捗・結果へ接続し、二重に開始しません。Gmailの状態と定義は承認後の既存の適用検証でも再照合します。

表示保存は直近12件、24時間までです。次の表示保存時に期限切れ／件数超過を整理します。1表示は最大200万文字で、BackupシートのWEB_VIEW行へ最大40000文字ずつ、1回最大10行の入出力で保存・検証します。Propertiesは小さなヘッダーと参照先、ブラウザは参照IDだけを持ちます。整理は所有者・ブック・保存ID・種別が一致するWEB_VIEW行の内容だけを消し、元のバックアップ、承認済みデータ、メール処理データ、履歴を削除しません。行自体も削除せず、既存の絶対行参照を維持します。

合成試験では `GFM_PREVIEW_DROP_READS=preview,prepareStart,importCheck,messagesList,messagesPrepare node scripts/preview-web.js` により、各操作の最初のサーバー完了後に元応答を無期限で保留できます。画面復帰または再読み込みで保存済み表示へ進むことと、`/test-stats` の要求数が増えないことを確認できます。この設定はローカル合成サーバーだけに適用されます。
