# スマホ用Web画面

Web画面は実行専用です。次の操作を利用できます。

| 操作 | 内容 |
| --- | --- |
| インポート | Gmailの既存フィルターとラベルをスプレッドシートへ追加。既存の編集を維持 |
| 全部適用 | Filters/Labelsから差分を取得し、確認後にまとめてGmailへ反映 |
| 選んで部分適用 | 差分からフィルター・ラベルを選び、依存ラベルを含めた確認後に反映 |
| 既存メールへ適用 | 有効な定義に一致するメールへラベル付与・アーカイブ・既読化 |
| 実行ログ | 日時・結果・エラー・バックアップIDを表示 |

Webには新規作成や編集フォームはありません。設定の編集は従来どおりスプレッドシートで行います。フィルター一覧やGmailデータは起動時に取得せず、操作画面を先に表示します。起動時の通信は未確認の前回結果・保存済み処理の概要と、設定済みスプレッドシート／Filters・LabelsのシートIDの確認です。設定へのリンク取得ではセル内容やGmailを読みません。実行ログの表示もGmailやFiltersの読み出しに依存しません。

## 配置

1. `npm test`、`npm run check`、`npm run build`を実行します。
2. 新規導入は通常のインストーラーを利用します。既存導入では更新したインストーラーの`GFM_updateInstalledCode`を実行します。配置先を手動変更すると整合性確認が停止します。
3. 初回のみ、**スプシに紐付く運用用GAS**で所有者が`GFM_enableWeb`を実行します。対象IDと共有状態を初期化します。メニューとWebは同じScriptProperties・ScriptLockを使用します。
4. 運用用GASを「ウェブアプリ」としてデプロイします。実行ユーザーは「アクセスしているユーザー」、アクセス範囲は「自分のみ」（`USER_ACCESSING` / `MYSELF`）です。
5. `/exec` URLをSafariで開いて所有者アカウントでログインします。「ホーム画面に追加」で起動用アイコンを置けます。

更新時は既存のWebデプロイを新しいバージョンに更新すればURLを維持できます。利用URL・作成先ID・個人設定を公開ソースに埋め込む必要はありません。既存メール処理には運用用GASの`gmail.modify`スコープが必要です。コードの更新に加えてWebデプロイを更新し、所有者アカウントで追加権限を再承認してください。インストーラーの権限は増えません。

## 適用の流れ

全部適用は「差分とバックアップの準備 → 1つの確認画面 → チェックして適用」の順に進みます。最初の操作で差分を取得し、バックアップの保存・読み返し検証まで段階ごとに進めます。準備中に表示する差分取得／バックアップ保存／読み返し検証の段階を確認してください。準備が終わると、追加・更新・削除件数、フィルターとラベルの変更前後、依存ラベル、転送・ゴミ箱への移動の注意、バックアップID、有効期限を同じ確認画面に表示します。一覧検索で絞り込んでも承認する全体の対象は変わりません。下部固定バーの実際の「上記の変更内容を確認しました」にチェックし、「全部Gmailに適用」を押すとジョブを受け付けます。承認前にGmailの変更や適用ジョブは開始しません。

選択適用は「対象選択 → 選択範囲と依存ラベルの確認 → チェックして適用」を維持します。選択0件のまま全部適用に切り替わることはありません。確認は15分で失効します。Gmailやスプシが変わった場合は再確認が必要です。全部適用の「内容を再確認」は最新の差分とバックアップを分割して準備し直し、新しい1つの確認画面で変更・消失した対象を案内します。選択適用の再確認は元の直接選択と継続元ジョブの範囲を維持して差分選択へ戻ります。

選択適用は最初は未選択です。選択したRuleKeyと依存ラベルキーの集合をBackupのSCOPEレコードとして分割保存・読み返しし、承認にはそのハッシュと件数を結び付けます。適用時はクライアントの新しい選択を受け入れません。選択外のフィルター定義は反映せず（共有ラベルの参照名は追従）、成功判定も選択対象に限定します。残っている差分の件数を完了画面に表示します。選択外に入力エラーがあっても、選択した対象が有効なら部分適用できます。復旧中の置換がある場合は、その復旧対象を含めて選択する必要があります。

Gmail側にしかないフィルターは自動削除しません。「無効」「削除予定」は反映時にGmail上の定義を削除する既存の仕様です。

## 既存メールへ適用

1. 必要に応じて「全部適用」「選んで部分適用」でGmailのフィルター設定を反映します。
2. 「既存メールへ適用」を開き、有効な定義の全件、またはチェックした対象を検索します。未反映のシート定義を使うこともできます。無効・削除予定の行は対象外です。実行できる3処理がない定義は選択できません。Labelsで新規作成・改名が未反映の参照先は、先にフィルター設定の反映から同期してください。既存メールの処理だけでラベルを作成・改名することはありません。
3. 検索リクエストの応答待ちと「ここまで検索済み・続行待ち」は別に表示します。続行待ちは「対象メールの検索を続ける」を押すまで次へ進みません。検索失敗時は原因を確認し、「検索を再試行」で同じ保存済み対象から続けます。検索中はメールを変更しません。検索済み件数は保存したメールIDの累計で、総対象件数と完了率は検索完了まで未確定です。
4. 検索完了後、0件の場合も「既存メールへの適用を確認」でフィルター別の件数、ラベル付与・アーカイブ・既読化、実行しない処理を確認します。未処理が1件以上の場合は確認チェックと専用ボタンで実行します。0件では確認内容を表示し、実行は無効です。検索の続行・再試行・再読み込みだけでは変更を承認しません。
5. 部分完了・失敗の場合は、状況とログを確認し、もう一度内容を確認して続行します。自動処理や時間トリガーは追加しません。

メール単位のAPIで処理し、同じスレッド内でも条件に一致しないメールには適用しません。対象は検索開始時刻より前のメールです。迷惑メール・ゴミ箱・下書き・送信済みは除外します。検索結果は時点をまたいで取得するため、Gmailの検索インデックス反映や外部からの変更により厳密な同時点スナップショットにはなりません。検索完了後は保存済みのIDだけを使用し、後から届いたメールを追加しません。同じメールが複数定義に一致した場合はフィルターごとに処理し、件数は**延べ件数**で表示します。

From、To（Cc/Bccを含む）、件名、Query、NegatedQuery、添付あり、チャット除外、サイズ条件をGmail API検索へ変換します。OR・否定は括弧で囲み、条件同士をANDで結びます。件名は連続する空白をまとめたフレーズで検索します。安全に変換できない括弧・引用符・制御文字・バックスラッシュや未認識の条件は実行を停止します。HasAttachment/ExcludeChatsのFALSEとサイズ比較unspecifiedは検索を制約しません。Gmail UIとAPIの検索は、アドレスのエイリアス展開などに違いがあります（[Googleの説明](https://developers.google.com/workspace/gmail/api/guides/filtering)）。

各リクエストは原則20秒・最大5ページ/バッチを目安とし、検索1ページ500件、更新1バッチ100件までに区切ります。各API呼び出し自体が遅延した場合は、この目安を超えることがあります。対象定義・メールIDはBackupのMESSAGESレコードへ分割保存し、Script Propertiesには小さな進捗だけを保存します。Backupを削除・並べ替え・直接編集すると対象の検証で停止します。検索後に選択した定義やラベルが変わった場合も更新前に停止するため、処理を中止して対象を再検索してください。

「残りの処理を中止する」は未処理分の続行を止めます。既に処理したメールを元に戻す機能はありません。更新APIの応答を失ったバッチは結果不明として未処理件数に含め、明示的な続行で同じIDへ再適用します。3処理は冪等なので、ラベル重複や転送などの副作用を起こしません。手動でラベル・未読・受信トレイを変更した場合は、再適用で確認済みの状態に戻ります。

## ラベルの反映

Labels.Nameが正です。確認画面でラベル作成/名前変更の前後を表示し、Gmail側が違う場合はシートの名前へ上書きします。選択フィルターに必要な管理ラベルもサーバーで選択対象へ追加し、承認画面に表示します。名前変更は同じラベルを使うメール・選択外のフィルターにも表示名が反映されます。選択外のフィルター定義自体は反映しません。

新規ラベルを先に作成・検証してからフィルターを反映します。名前のみ変わる場合はフィルターを作り直しません。選択件数と集計にはラベルを含みます。各ラベルをフルパスで管理し、希望名重複や別IDの同名ラベルはエラーです。

## 通信断・ログ

通信が切れても適用を自動再送しません。結果不明の画面で実行IDを表示し、保存済み結果か同じ実行IDのログを確認できます。未確認の結果はサーバーに保持し、再読み込み後にも表示します。部分完了や復旧が必要な場合は[復旧手順](recovery.md)を参照してください。

スプシへの直接のセル編集はGASのロックに参加しません。Webで適用する間は同時の直接編集を避けてください。全行とGmailのfingerprintを承認時・適用時に照合しますが、Sheets APIに条件付きセル更新のトランザクションがないため、外部編集との極めて短い競合区間は完全には排除できません。

## デザイン・ローカル検証

[デジタル庁デザインシステム](https://design.digital.go.jp/dads/)のカラー、文字、ボタン、入力欄、結果表示を参考にした独自HTML/CSSです。ロゴは使っていません。UIの外部CDN依存はありません。

`node scripts/preview-web.js`で合成データのプレビューを起動し、`http://127.0.0.1:4179/`で操作できます。`GFM_PREVIEW_CHANGES=1`を付けると2件の差分、`GFM_PREVIEW_LOST_APPLY=1`を付けると適用応答の喪失を再現できます。実際のWeb/Sync/Sheetsのコードにテスト用Googleサービスを接続し、実アカウントは変更しません。このサーバーはGASへ同梱されません。

既存メールの応答喪失は`GFM_PREVIEW_LOST_MESSAGES=1`で再現できます。ローカルの既存メールは合成IDと模擬更新のみです。


## 画面を離れた場合

画面を再表示したとき（visibilitychange/pageshow）は、待機中の古い応答から画面を切り離し、保存済みのリクエストIDで状況を取得し直します。通常の応答待ちが45秒続いた場合も、状況確認画面へ切り替えます。状況確認自体には10秒の待ち時間上限があり、失敗しても再確認できます。

設定適用の結果、インポートの結果、既存メールの検索・処理状況を復元できます。結果確認では変更処理を自動再送しません。受け付けたか分からない場合や、サーバー処理の状態が7分以上更新されない場合は、未確定として表示します。変更操作の古い応答が後から返っても、復元後の画面や別の操作を上書きしません。差分・確認画面などの読み取りは、同じ処理の状況確認中なら遅れて届いた表示データを利用できます。別の操作へ進んだ場合は、その読み取り応答も破棄します。

再読み込み対策としてsessionStorageへリクエストID・操作名・実行IDと、表示済み画面の参照IDだけを保存します。承認トークンやメールの定義は保存しません。埋め込みブラウザで保存が拒否された場合も、同じページ内の復帰処理とサーバーの既存結果保存を使用できます。サーバーのリクエスト別記録は直近32操作を保持し、それより古いものは実行ログで確認します。メール処理は開始時点でリクエストIDと実行IDを同じチェックポイントに保存します。復帰用のresume APIは所有者の小さなチェックポイントだけを読み、Gmail/Filters/Backupの取得や実行ロックを必要としません。

既存メールの保存済み`SCANNING`は検索の保存地点であり、現在もサーバー実行中という意味ではありません。状況画面の再読み込みでは同じ実行IDの保存済み対象と次の操作を取り出します。応答を失った検索はリクエストの完了を確認するまで未確定と表示し、最後に保存できた検索済み件数を示します。「状況を更新」で確認できない場合は「操作に戻る」から「保存済みの既存メール処理を確認」を開きます。状況の取得は操作ロックで実行中の要求と排他され、応答が確認できた状態から手動で続けます。

この対応は開始済みの1回分の処理と画面復帰のためのものです。大量メールの検索・適用は従来どおり分割し、部分完了後の次の実行には確認が必要です。画面を閉じたまま全バッチを自動完了するスケジューラーは含みません。

適用カード内の長いラベル名・検索条件・アドレス・ID・JSONは画面幅内で折り返します。文字数で値を切り詰めず、スマホでは変更前後を縦に表示します。


## 差分・確認画面の保存と復帰

差分、全部／選択適用の確認、インポート確認、既存メールの対象一覧と適用確認は、表示データをサーバーへ保存します。同じタブの再読み込みでは、通信中ならリクエストの状況を確認し、表示済みなら保存済み画面を取得します。元の応答が届かなくても、完了記録から表示結果を取り出せます。取得には10秒の上限があり、失敗・期限切れ・不明の場合は「取得し直す」または「操作に戻る」へ進めます。

選択適用では操作段階、ALL/SELECTEDと選択キーをサーバーで保持します。チェックを変更するたびに保存し、失敗時は画面上で案内します。保存がサーバーへ届く前にタブを破棄した場合、その最後の変更は戻らない場合があります。確認画面から「差分に戻る」は元の保存済み差分とユーザーの選択を開きます。確認に追加した依存ラベルを、ユーザーが直接選択したキーへ追加しません。「差分を再取得」または「取得し直す」を押した場合に、新しい差分を計算します。

復元ではプレビュー・バックアップ作成・適用を自動再実行しません。確認チェックは毎回未選択で、適用には再び明示的な承認が必要です。別の差分確認、設定変更、確認の15分期限で失効した確認内容は、実行を無効にした状態で復元し、「内容を再確認」へ案内します。承認済みのフィルタージョブがあれば保存済みの進捗・結果へ接続し、二重に開始しません。Gmailの状態と定義は承認後の既存の適用検証でも再照合します。

表示保存は直近12件、24時間までです。次の表示保存時に期限切れ／件数超過を整理します。1表示は最大200万文字で、BackupシートのWEB_VIEW行へ最大40000文字ずつ、1回最大10行の入出力で保存・検証します。Propertiesは小さなヘッダーと参照先、ブラウザは参照IDだけを持ちます。整理は所有者・ブック・保存ID・種別が一致するWEB_VIEW行の内容だけを消し、元のバックアップ、承認済みデータ、メール処理データ、履歴を削除しません。行自体も削除せず、既存の絶対行参照を維持します。

合成試験では `GFM_PREVIEW_DROP_READS=preview,prepareStart,importCheck,messagesList,messagesPrepare node scripts/preview-web.js` により、各操作の最初のサーバー完了後に元応答を無期限で保留できます。画面復帰または再読み込みで保存済み表示へ進むことと、`/test-stats` の要求数が増えないことを確認できます。この設定はローカル合成サーバーだけに適用されます。


READY確認の再取得は、最新の準備ID・設定検証・トークン発行を同じ操作ロック内で行います。並行した差分再取得や別の確認準備が割り込んだ場合、古い確認へトークンを戻しません。準備中の進捗は引き続きロックなしで読めます。

保存期限切れ／件数超過の表示データが破損して整理できない場合、その疑わしいセルは保持し、新しい画面の保存を続けます。隔離した保存先の小さな記録は直近12件まで保持し、それより古い記録だけを破棄します。破損したセルや他種別のバックアップを自動削除しないため、隔離セルの容量は通常の12表示・24時間の自動整理対象外です。

## 確認の有効期限と再確認

フィルター適用・既存メール適用・インポートの確認画面は、サーバーが返した期限時刻を日本時間で表示し、有効／期限切れ・設定変更・Gmail変更・別操作による失効を区別します。期限時刻に達すると最終承認できません。準備チケットとWebのトークンに別の期限がある場合は、早い方を使い、画面復元や遅いトークン発行で延長しません。

確認画面を非表示にすると承認チェックを外して操作を無効にします。復帰時、再読み込み時、表示中の定期確認ではサーバーの現在時刻と最新状態を再照合します。「確認状態を更新」でも再照合できます。端末の時計がずれていても期限の基準には使いません。接続できない間は実行できず、再取得後もチェックを入れ直します。インポートにも内容を確認したチェックが必要です。

期限切れや失効した画面の「内容を再確認」から、その場で最新の内容へ進めます。フィルターは元のユーザー選択を可能な範囲で保持した新しい差分へ戻り、依存ラベルを再検証してから新しいバックアップ・適用確認へ進みます。消失した対象、適用できなくなった対象、変更された対象・依存ラベルはキー付きで表示し、再読み込み後も案内を保持します。古い承認チェックは引き継ぎません。自動で確認準備や適用には進みません。

既存メールは定義が一致すれば同じ保存済みIDと最新の処理済み／残り件数を再確認します。選択した定義や依存ラベルが変わった場合は元の残り処理を中止し、保持できた選択を最新一覧へ戻します。対象を明示的に検索し直してから、件数・処理内容を再確認してください。既に完了したメールの変更は戻りません。インポートは最新の未登録件数を取得し直します。

15分の期限は最終承認までのものです。受け付け済みのフィルタージョブは承認画面の期限と独立して継続し、古い確認画面も進捗・結果へ接続します。期限を理由に同じジョブを再送したり、自動で再承認したりしません。

合成ブラウザ試験では `GFM_PREVIEW_CONTROLS=1 GFM_PREVIEW_CHANGES=1 node scripts/preview-web.js` で起動し、ローカルの `POST /test-control` に `{"advanceMs":900000}` を送るとサーバー時刻を15分進められます。`{"subject":"再確認する変更"}` は最初の合成フィルターのシート定義だけを変更します。画面復帰／「確認状態を更新」／再読み込みで再判定できます。この制御は明示した環境変数があるときだけ有効で、通常は404です。実Gmailや配置するGASには含まれません。


## 一覧の検索・入力エラーと設定への移動（Issue #9）

全部適用の差分、選択適用の差分、既存メールの対象一覧には「一覧を検索」と「入力エラーのみ表示」があります。送信元、件名、ラベル名、表示した条件やエラー理由などの部分一致で絞り込みます。英字の大文字・小文字と全角・半角を正規化します。取得済みのカード内の情報だけを使い、文字入力・絞り込み・解除でGmailやSheetsを再取得しません。Gmailのメール検索を開始する操作とは別です。

表示件数／一覧全体の件数／入力エラー件数に加え、選択適用と既存メールでは全体の選択件数と非表示の選択件数を表示します。検索・エラー絞り込み・「絞り込みを解除」・Escapeキーで表示を変えても選択は保持します。検索結果が0件の場合は解除操作を案内し、解除後は検索入力へフォーカスを戻します。

「表示中の選択可能な対象をすべて選択」「表示中の選択可能な対象を解除」は、その時点で表示されている有効な対象だけに作用します。非表示の対象は変更しません。非表示の選択も次の確認に含まれるため、件数と確認画面を確認してください。入力エラーや既存メールで実行できる処理がない対象は選択できません。

入力エラーのカードにはFilters／Labelsの区別、対象キー、修正理由、設定シートへのリンクがあります。全部適用はエラーが1件でもあれば進めません。「正しい対象を選択して適用」は同じ差分を選択適用へ切り替えるだけで、自動選択・適用はしません。この切り替えと選択は保存対象です。既存メールの全件検索もエラーがあれば停止し、正しい対象の明示選択を案内します。

操作画面と各操作の案内から「設定スプレッドシートを開く」で、サーバーに設定された管理用ブックを新しいタブで開きます。入力エラーからはFilters／Labelsへ進み、一意の行メタデータと現在のキーを照合できる場合に行位置も付けます。一意に照合できない場合はシートへ案内します。行リンクは一覧取得時点の目安であり、並べ替え後は表示したRuleKey／LabelKeyも確認してください。URLを入力して任意のブックを開く機能はありません。

リンクを開いても元の画面・保存済み表示・選択は保持します。リンクを開いた一覧は、そのまま次の確認へ進めなくなります。「差分を再取得」「対象一覧を再取得」で最新の一覧を確認し、対象を選び直して確認へ進んでください。最終確認から開いた場合は承認チェックを解除し、「内容を再確認」から新しい確認を行います。単なる確認状態の更新では古い承認を再有効化しません。別の場所で直接シートを編集した場合も、サーバーで設定の変更を検出すると古い差分・確認からの適用を拒否します。検索語とエラー絞り込みは一時的な表示条件で、再読み込み後は解除されます。


## 選択件数と次の操作の固定表示（Issue #10）

差分一覧、選択適用、既存メールの対象一覧は、現在の件数と主要な次の操作を画面下部に表示します。選択件数は検索で隠れた対象も含む全体の件数です。フィルター／ラベルの内訳と非表示の選択件数を確認してから進んでください。検索結果が0件でも、非表示の選択があれば確認／メール検索へ進めます。選択自体が0件、全部適用で入力エラーがある場合、設定リンクを開いた後の再取得前、通信中は進めません。

最終確認では、変更対象または既存メールの未処理件数と、明示確認のチェック・適用ボタンを同じ下部バーに表示します。チェックは自動で入りません。対象0件、入力エラー、期限切れ、非表示からの復帰後の状態確認中は適用できません。期限・失効理由は一覧末尾の案内に表示します。「内容を再確認」で内容を更新し、改めてチェックしてください。下部のボタンも通常のリクエスト管理を通るため、通信中の連打で同じ処理を二重送信しません。

一覧直前の「次の操作へ移動」はキーボードで下部バーへ移動するためのリンクです。読み上げでは「選択件数と次の操作」の領域を利用できます。件数・確認チェック・実行の順で操作でき、狭い幅では縦に並びます。表示が大きいときやキーボード表示で高さが狭いときは、バー内もスクロールできます。

カードの最後やエラーがバーに隠れないよう、バーとスマホ用メニューの実測高さに応じた余白を確保します。セーフエリアのCSSに加え、対応ブラウザではvisualViewportの変化からソフトキーボード等の表示領域を考慮します。実機のキーボード／セーフエリア挙動は端末・ブラウザでも確認してください。全部適用の統合確認画面も同じバーで全体の件数、実際の確認チェック、適用ボタンを表示します。検索結果が0件でも承認対象の全体は変わりません。入力エラー・変更なしの分岐では適用ボタンを無効にします。


## 全部適用の分岐と準備の復旧（Issue #11）

入力エラーがある場合はバックアップを作らず、Filters／Labelsの区別、対象キー、理由、修正先リンクを示します。修正後に「差分を再取得」で全部適用の準備をやり直せます。「正しい対象を選択して適用」は新しいSELECTEDの差分を取得し、選択0件から始めます。変更がなければ「変更はありません」と案内し、バックアップ・承認トークン・適用ジョブを作りません。Gmail側だけに存在するフィルターは削除しません。

準備中のタブ非表示→復帰、元応答喪失後の「状況を更新」、再読み込みは、保存した準備IDと段階を読みます。準備やバックアップを最初から作り直しません。確認画面から「操作に戻る」を選んだ後も「保存済みの適用確認を開く」で復帰できます。準備トリガーが消えた場合は状況取得で継続を登録し直します。トリガーが存在しても5分以上更新がなければ保存した段階から最大3回修復し、それでも動かなければ権限・割り当ての確認と明示的な再取得を案内します。

バックアップの保存前にIDを保存します。保存完了直後に実行が強制終了しても、同じIDを読み返して検証し、重複保存せず続けます。保存途中で不完全になったバックアップは上書き・削除しません。その理由を表示して準備を停止し、利用者の「差分を取得し直す」で新しい準備へ進みます。SELECTEDの範囲も保存後に読み返して照合します。

初回のFilters／Labelsキー初期化は各シートのキー列を1回で書き、行メタデータは500件以下のSheets API batchUpdateで作成します。行メタデータの検索・読み返しはSheets APIの一括取得を使います。合成試験では各1200行の初期化がキー列2回、メタデータ6回（500/500/200 × 2）、初期化内のメタデータ検索4回で完了し、行ごとの追加呼び出しは0回です。READ／BACKUP／VERIFY_BACKUPの時間は既存の段階計測で保存します。

ローカルのスマホ検証例（すべて合成データ）:

```sh
GFM_PREVIEW_CHANGES=1 GFM_PREVIEW_LABELS=1 GFM_PREVIEW_RISKS=1 GFM_PREVIEW_BLANK_KEYS=1 GFM_PREVIEW_CONTROLS=1 node scripts/preview-web.js
```

`GFM_PREVIEW_ERRORS=1` はFiltersとLabels両方の入力エラー、環境変数なしは変更なし、`GFM_PREVIEW_ROWS=120` は長い一覧を用意します。`GFM_PREVIEW_JOB_INTERVAL_MS=3000` で準備段階を見やすくできます。`GFM_PREVIEW_DROP_READS=prepareStart` を加えると最初のALL準備の元応答だけを保留します。復帰・再読み込み・確認状態の更新後も `/test-stats` の `requestCounts.prepareStart` と `backupCount` が各1、`filterWrites` が0であることを確認してください。明示チェック・適用後だけ `filterWrites` が増えます。既存の `/test-control` の `advanceMs` で期限切れ、`subject` で設定変更を合成でき、再確認でREADから新しい1つの確認へ進むことを検証できます。


新しいタブやブラウザ再起動でsessionStorageの表示IDがない場合も、bootが準備IDに対応する所有者・スプレッドシートの表示IDを返し、保存した画面を検証してから復帰します。SELECTEDでは直接選択したキー、依存ラベル、元の差分への戻り先を分けて保持し、期限切れ後の再確認や狭めた継続範囲を全部適用へ広げません。保存した表示が欠落・破損・期限切れの場合は、適用の代わりにSELECTEDで対象を明示的に選び直します。保存済み状況を取得できない場合の「取得し直す」も、選択0件のSELECTEDから再開します。
