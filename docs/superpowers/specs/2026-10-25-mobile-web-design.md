# Gmail Filter Manager スマホ用Web画面の設計案

状態: 実装前の設計案。ユーザーの指定は「携帯で操作が完結するWeb画面」「デジタル庁デザインシステムを参考にする」。以下の画面構成・実装方法は提案者が選んだ初期案。

## 目的と範囲

iPhoneのSafariで、自分のGmailフィルターの取り込み、検索、新規作成、編集、削除予定の指定、変更確認、Gmailへの反映、実行結果の確認まで行えるようにする。編集のためにSheetsアプリを開く必要をなくす。

既存のスプレッドシート、紐付けGAS、Filters/Diff/History/Backup、同期処理を利用する。別サーバー、MCPプラグイン、定期ポーリングのCommandsシートは追加しない。Googleアカウント所有者だけが利用する。スプレッドシート上の編集と従来メニューも利用できる。

## 画面と操作

### フィルター一覧

サービス名、管理件数、直近の結果を表示。検索はメモ、From、To、Subject、Query、ラベルを対象にする。状態で絞り込める。カードにはメモまたは条件、ラベル、状態、未反映の有無を表示。20件ずつ表示し、続きを読む操作を用意する。実際の件数を読み取り、108件などの固定値を製品に書かない。

「新規フィルター」「Gmailから取り込む」「変更内容を確認」の入口を置く。取り込みは追加予定件数と既存の編集を維持する旨を表示し、実行ボタンで確定する。

### フィルター編集

縦一列のフォームで、メモ、状態、From、To、件名、含む条件、含まない条件、添付、チャット除外、サイズ比較とバイト数、ユーザーラベル、既読・アーカイブ・迷惑メール除外・重要・重要でない・スター・ゴミ箱・転送を編集する。既存ラベルと検証済み転送先は選択式にする。追加ラベルIDの配列は「詳細設定」にまとめ、既存の値を失わず編集できるようにする。

添付・チャット除外は「指定なし/はい/いいえ」の3値、サイズ0を保持。生のOriginalJson等のシステム列は編集させない。未知のフィールドは元データを保持し、変更できない理由がある場合は明示する。

保存ボタンは「変更を保存」。保存先はFiltersであり、保存直後にGmailへ反映しないことをフォームと完了表示で伝える。未保存で戻る際に確認する。

削除は物理行削除ではなく「削除予定」にする。無効化も現行仕様では反映時にGmail上のフィルターが削除されるため、選択時に説明する。削除予定から有効に戻せる。Gmail側にしかないフィルターを一括削除する操作は提供しない。

### 変更確認と反映

「変更内容を確認」で既存previewを実行。追加・更新・削除・変更なし・入力エラーの件数を日本語で表示。変更項目ごとに変更前/変更後を縦に表示し、横長JSON表だけにしない。ラベルIDは取得済みラベル名を併記する。必要な原本は詳細表示できる。

入力エラーがある場合は編集対象への入口を表示し、反映できない理由を説明。変更なしの場合は反映不要とする。Gmail側のみの定義は維持されることを表示する。

「反映の確認へ」で既存prepareを実行し、バックアップを作成・検証する。確認画面には同じRunIdの差分、件数、ゴミ箱・転送の注意、置換時の一時的な新旧同時有効、バックアップ作成済みを表示。「この変更をGmailに反映」を押したときだけapplyを実行する。15分の承認期限、設定変更後の再確認、使い捨て承認状態をサーバーで検証する。クライアントが送った件数や差分を実行根拠にしない。

結果は成功、一部完了、復旧が必要、失敗を区別し、実際の完了件数と次の操作を示す。復旧が必要な場合、同じ適用を自動再送しない。既存verifyで整合性確認できる。

### 履歴

Historyを新しい順に20件ずつ表示し、日時・操作・結果・エラー・関連RunIdの詳細を読めるようにする。バックアップの有無とSnapshotIdも関連付ける。生の巨大なバックアップJSONを初期画面に送信しない。バックアップの自動復元・自動削除は今回作らない。

### 共通

「フィルター」「変更確認」「履歴」の3つの主要移動先を置く。スマホは下部、広い画面は上部でもよい。iPhoneのセーフエリアと画面キーボードを考慮し、固定要素でフォームやボタンを隠さない。

読込中、処理中、空の状態、認証不足、通信失敗、同時編集を区別する。実行中は二重送信を防ぐ。通信失敗時は結果不明として履歴を再読込し、成功を推測しない。

## デザイン

参考: https://design.digital.go.jp/dads/ （調査時 v2.18.2）。デジタル庁のサービスであると誤認させるロゴや表現は使わない。

白背景、青の主操作、濃い本文、薄いグレーの区切り。主操作は塗り、補助は枠線やリンクを使い分ける。本文16px以上、主要ボタンは高さ48px以上を提案値とする。日本語の読みやすいサンセリフ、余白8px単位、明確な見出し、フィールドごとのラベルと説明を使う。

状態やエラーは色と文字を併用。インラインのエラーとフォーム先頭のエラー案内を用意する。キーボード操作、明示的フォーカス、見出し構造、aria-liveの結果通知、拡大表示に対応する。320px幅から横スクロールなしで基本操作可能にする。DADSの完全準拠やアクセシビリティ認証取得とは表現しない。

HTML/CSS/JavaScriptをGAS HTML Serviceに同梱する。フレームワークや外部CDNを必須にしない。トークン・コードを転載する場合は元のライセンスと帰属表示を確認して同梱する。独自に参考実装する場合もREADMEに参考元を記載する。

## 技術構成

紐付けGASにdoGetとHTMLファイルを追加。google.script.runで用途を限定したサーバー関数に接続する。GETは画面表示のみで、URLにアクセスするだけで取り込み・保存・Gmail変更を実行しない。画面の初期HTMLに個人データを直接埋め込まず、認証済み呼び出しで取得する。

Webアプリは自分のみアクセス可能（MYSELF）、アクセスするユーザーとして実行（USER_ACCESSING）を初期選択にする。各サーバー関数でも有効ユーザーと対象スプシの所有者を照合する。任意のスプシID・関数名を呼び出せるAPIは公開しない。Googleの公開設定・Workspaceポリシーでこの組合せが選べない場合は、公開範囲を広げず原因と代替設定を提示する。

対象スプシIDはScriptPropertiesに設定し、openByIdで開く。ソースに個人用IDやメールを埋め込まない。所有者が既存スプシから実行する初期化関数でIDを登録し、所有者を検証する。新規インストールにも同じ初期化手順を案内する。

共有ランタイムを抽出し、メニューとWebの両方でScriptLockを使う。DocumentPropertiesへの依存はScriptPropertiesの共通状態に移す。所有者がスプシから初期化する際に既存のGFM状態を読み、pending/cleanup/importCompleteを保持してコピーし、読み返してから移行済みとする。preview/preparedは移行時に無効化。既存移行先と衝突したら上書きしない。旧状態を削除せず、移行済みマーカーがあれば再コピーしない。Webは初期化前に実行できない。以後のメニューも同じ状態を参照し、古い状態へ戻らない。

既存Core/Sync/Gmailを再利用。Sheetsに編集可能列だけを書き込む機能を追加し、RuleKeyのメタデータIDで行を指定する。読み込み時の行バージョンをサーバーで照合し、他の編集を黙って上書きしない。文字列はRAW等でそのまま保存し、数式として実行させない。保存時にプレビューと承認準備を失効させる。

新規作成は同一の発行済みRuleKeyで再送しても重複作成しない。編集内容はサーバーで許可リスト・型・長さ・Coreの条件検証を行う。エラー修正のための無効行の保存は可能にし、変更確認で反映不可を示す。画面表示はtextContent等を利用し、ユーザー入力やGmail由来の文字列をHTMLとして挿入しない。

反映確認はサーバーのprepareに結びついたランダムトークンを発行し、アカウント・スプシ・RunId・fingerprintに対応させる。applyはトークン、保存済みticket、有効期限、最新状態を検証し、一回のみ使用する。クライアントの任意のapproved=trueだけで実行を受け付けない。既存メニューからの適用も従来の確認を維持する。

通信は同期処理を非同期UIから呼ぶ。既存の適用上限と部分完了・復旧ジャーナルを維持する。長い操作は処理中表示と操作禁止を行い、接続切れで自動再実行しない。タイムアウト後はHistoryと保存済みRunIdを照合する。新たな常駐ジョブ基盤は追加しない。

scripts/build.jsをHTMLおよび追加JSの同梱に対応させ、従来どおりインストーラーの安全な更新経路を使う。バージョン付きWebアプリを配置し、将来の更新では既存deployment IDを更新してURLを維持する。必要な初期化とWeb配置の操作を手順化する。Web URLは設定・出力で扱い公開ソースに個人用設定を入れない。

## 確認と完了条件

- 既存テストを維持し、共有状態の移行、権限拒否、編集競合、システム列の変更拒否、文字列保存、新規再送、古い承認と二重反映の拒否を実質的なテストで確認する。
- 合成データで取り込み→編集→差分→承認→反映→履歴までブラウザ検証。320/390/768px、拡大表示、フォーカスと入力エラーを確認する。ローカル検証と実GAS検証を区別する。
- 実アカウントでは一覧、履歴、追加0件の取り込み、変更0件のプレビューを確認する。既存108件は可変の検証時点の値として扱う。実Gmailへの書き込みを伴う試験は具体的な差分への承認なしに行わない。
- GitHubの公開コードと実GASの配置内容を照合し、利用URLとホーム画面への追加手順を報告する。iPhone実機をこちらから操作できない場合はその限界を記載し、ブラウザの幅指定検証だけを実機検証と呼ばない。

## 実装時に任せる事項

CSSの細かな余白・アイコン、内部分割、ページ送りAPIの形、テスト用サーバーの形式は実装者が選択できる。ライブラリ導入は必要最小限。今回の設計のためだけに外部サービスや新しいCloudプロジェクトを作らない。
